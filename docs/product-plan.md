# 障害者くらしナビ プロダクト・開発計画

最終更新: 2026-08-30

## 名称とドメイン

- 正式名称: **障害者くらしナビ**
- メインドメイン: **`shogaisha-kurashi.com`**
- 現在の名称「UniPark」は、リブランディングを実装するまでは既存コード・画面内で継続して使用する
- 駐車場マップは、障害者くらしナビ内の一機能として引き継ぐ

## 目指すもの

障害者くらしナビは、現在の「UniPark（障がい者割引のある駐車場マップ）」から、将来的に障害のある人が生活に必要な支援情報をまとめて確認できる総合アプリへ発展させる。

> 知らなかったせいで、受けられる支援を逃す人をなくす。

中核機能は、居住自治体、手帳種別、等級、年齢などの利用者条件をもとに、利用できる可能性のある制度・割引・施設だけを提示することである。

## 最初の完成ライン

最初の対象者を「中野区在住・身体障害者手帳4級」とし、次の状態を完成ラインとする。

- 国、東京都、中野区の制度をカテゴリー別に確認できる
- 利用できる可能性を、根拠とともに確認できる
- 必要書類、申請方法、申請窓口、公式情報URLを確認できる
- すべての情報に最終確認日がある
- 条件不足や未確認を「対象外」と誤判定しない
- 既存の駐車場マップを公開し、検索エンジンから詳細情報へ到達できる

## 判定の基本方針

制度の対象判定は次の区分を基本とする。

1. 利用できる可能性が高い
2. 追加条件の確認が必要
3. 個別相談が必要
4. 現在の条件では対象外と確認できる

「情報が見つからない」「条件が入力されていない」「公式情報だけでは判断できない」を、対象外として扱わない。

## URLとレンダリング方針

SEOは、検索エンジンへ完成したHTMLと適切なメタ情報を返すことを重視する。地図の操作部分だけをクライアント側で動かし、検索対象となる本文はサーバー側で生成する。

| URL | 役割 | レンダリング方針 |
|---|---|---|
| `/` | UniParkのトップページ | 静的生成 |
| `/map` | 現在地・地図範囲から探す | CSR |
| `/parking/[id]` | 駐車場詳細 | 事前生成。DB移行後はISR |
| `/tokyo/[municipality]` | 地域別一覧 | ISR |
| `/facility/[id]` | 無料・割引施設詳細 | ISR |
| `/systems` | 条件に合う制度一覧 | サーバー生成とCSRの併用 |
| `/system/[id]` | 自治体制度詳細 | ISR |
| プロフィール・お気に入り | 利用者固有情報 | CSRまたは認証付きSSR |

`/parking/[id]` は、名称、住所、割引、営業時間、情報源などをServer Componentで生成する。MapLibreを使う周辺地図だけをClient Componentへ分離する。ページごとのメタデータ、構造化データ、404、サイトマップへの収録にも対応する。

## Track A: 公開・SEOの土台

### A1. 地図を `/map` へ移す

- 現在の `/` の地図画面を `/map` へ移動する
- 既存ページの「マップに戻る」リンクを修正する
- PWAの起動先とオフラインキャッシュを確認する
- 地図、地域一覧、駐車場詳細の既存動作を維持する

### A2. SEOトップページを作る

- `/` をServer Componentで作る
- UniParkの目的、現在提供している機能、対応地域を説明する
- 地図、地域一覧、将来の制度検索への導線を置く
- title、description、canonical、OGPを設定する
- `robots.ts` と `sitemap.ts` を整備する
- WebSiteまたはWebApplicationの構造化データを追加する
- 見出し、内部リンク、キーボード操作、読み上げを確認する

### A3. 駐車場詳細をサーバー生成する

- `/parking/[id]` のページ全体にある `use client` を外す
- データをサーバー側で取得する
- 地図だけをClient Componentへ分離する
- `generateStaticParams()` で既存駐車場を事前生成する
- `generateMetadata()` でページ固有のメタデータを作る
- 存在しないIDは `notFound()` で404にする
- 適切なSchema.org構造化データを追加する
- 将来Supabaseへ移行した段階でISRへ切り替える

## Track B: 中野区・身体障害者手帳4級の制度MVP

### B1. 調査範囲とデータ形式を決める

調査対象は国、東京都、中野区とし、次のカテゴリーを棚卸しする。

- 手当・給付金
- 医療費助成
- 税金・年金
- 公共料金・通信・NHK
- 交通機関・ETC・有料道路
- 駐車禁止除外
- 補装具・日常生活用具
- 住宅・就労・福祉サービス
- 相談窓口
- 無料・割引施設
- 防災・選挙・行政手続き

### B2. 公式情報から制度を収集する

- 自治体、国、制度実施機関の公式情報を一次情報とする
- 制度ごとに対象条件と根拠箇所を記録する
- 公式URLと最終確認日を必須にする
- 情報の不一致や判断不能な条件を注記する
- 対象、要確認、対象外を根拠付きで整理する

### B3. 最小データモデルとAPIを作る

初期は既存方針に合わせ、静的TypeScriptデータとRoute Handlersで実装する。制度構造と利用実態が固まってからSupabase/PostgreSQLへ移行する。

最低限、次の情報を保持する。

- 制度ID、制度名、実施主体、対象地域、カテゴリー
- 支援内容
- 手帳種別、等級、年齢、所得、その他の条件
- 必要書類、申請方法、申請窓口
- 公式URL、最終確認日、注意事項
- 情報の確実性と更新履歴

API契約とTypeScript型を先に更新し、その契約に合わせてデータと画面を実装する。

### B4. 制度一覧と詳細を作る

- `/systems` に利用できる可能性のある制度を表示する
- `/system/[id]` に条件、支援内容、申請方法、出典を表示する
- `/tokyo/nakano` に中野区の制度と施設をまとめる
- 初期プロフィールは「中野区・身体障害者手帳・4級」とする
- 年齢、所得など未入力の条件は要確認として表示する
- 最初はログインを必須にせず、必要ならブラウザ内へ条件を保存する

## 実施順序

Track AとTrack Bを並行して進める。ただし、一度に大きく実装せず、次の完成単位で統合する。

1. 現行ルート、SEO、制度データ契約の整理
2. `/map` への移動と既存導線の修正
3. SEOトップページ
4. `/parking/[id]` のServer Component化
5. 制度の調査フォーマット確定
6. 中野区・東京都・国の制度調査
7. 制度API契約と静的データ
8. 制度一覧、制度詳細、条件判定
9. SEO、アクセシビリティ、型、lint、テスト、主要導線の統合検証

## 将来の拡張

制度データ、ユーザープロフィール、投稿・修正依頼が増えた段階で、Supabase上のPostgreSQLとPostGISへ移行する。想定する主なテーブルは次のとおり。

- `places`
- `benefits`
- `programs`
- `eligibility_rules`
- `municipalities`
- `sources`
- `revisions`
- `user_profiles`
- `favorites`
- `reports`

位置情報は `geography(Point, 4326)` で管理する。DB移行は先行目的にせず、静的データで制度の構造と利用価値を検証してから実施する。

## 品質基準

- 公式情報URLと最終確認日を必須にする
- 不明情報を「なし」と断定しない
- API契約と型を先に更新する
- App Router構成を維持する
- 地図以外のSEO対象本文はサーバー側でHTMLを生成する
- 実装後にlint、typecheck、testを実行する
- WCAGを意識し、キーボード操作、色のコントラスト、読み上げ順を確認する
